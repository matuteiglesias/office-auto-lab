# systemd user automation

**Status:** canonical
**Audience:** operators installing local user timers
**Owner:** `systemd/user/` and office-auto-lab maintainers
**Verified against:** estate-surface governance alignment round

## Safety boundary

The tracked unit files are now **machine-neutral**. They do not contain a
checkout path or username. Each service reads one installed environment file:

```text
~/.config/office-auto-lab/runtime.env
```

That file records the exact checkout root, Python interpreter, evidence roots,
and any explicitly configured advisory governance context for the current
operator. It is generated by the installer and is not committed.

Do not hand-edit tracked unit files to point at another checkout. Re-run the
installer so the installed runtime identity remains explicit and reproducible.

## Optional estate governance context

`projects` owns two context contracts that Office can consume without acquiring
their semantic authority:

- `context:github-repositories@1` from
  `projects/generated/github-repository-context.json`;
- `registry:estate-surfaces@1` from `projects/estate/surfaces.json`.

The repository context is generated state. Refresh it from the `projects`
checkout before wiring it into a long-lived Office install:

```bash
PROJECTS_ROOT="/absolute/path/to/projects"
cd "$PROJECTS_ROOT"
python3 scripts/repository_context.py generate
```

`estate/surfaces.json` is reviewed source, not generated output.

When configured, the installer writes the absolute paths into `runtime.env` as:

```text
OFFICE_REPO_CONTEXT_JSON=...
OFFICE_SURFACE_CONTEXT_JSON=...
```

These inputs are advisory. They may enrich repository identity and expose
surface promotion/remediation drift in Office artifacts, but they do not change
Carry State, horizon, priority, Principal posture, selection, escalation, or
canonical human state.

Do not configure a context path merely because the file exists. The file should
come from the intended `projects` control-plane checkout and should be refreshed
according to that repository's own governance cadence.

## Render-only preflight

Before mutating a user systemd session, render the exact configuration into a
temporary directory:

```bash
PROJECTS_ROOT="/absolute/path/to/projects"

PYTHONPATH=src python3 src/office_runtime/scripts/install_systemd.py render \
  --repo-root "$(pwd)" \
  --python-bin "$(command -v python3)" \
  --evidence-root "$HOME/repos" \
  --evidence-root "$HOME/Documents" \
  --repo-context-json "$PROJECTS_ROOT/generated/github-repository-context.json" \
  --surface-context-json "$PROJECTS_ROOT/estate/surfaces.json" \
  --out /tmp/office-systemd

systemd-analyze verify /tmp/office-systemd/units/*.service \
  /tmp/office-systemd/units/*.timer
```

Both context flags are optional. Omit one or both when the corresponding
control-plane artifact is intentionally unavailable.

The renderer fails if the checkout/Python/evidence roots are not absolute and
existing, if a configured context path is not an absolute existing file, if a
required runtime script is missing, or if a tracked service still contains a
machine-specific `/home/matias/...` path or unresolved template marker.

CI executes this render/verification path without touching a live user session.

## Installation

From the checkout that should own local Office automation:

```bash
PROJECTS_ROOT="/absolute/path/to/projects"

PYTHONPATH=src python3 src/office_runtime/scripts/install_systemd.py install \
  --repo-root "$(pwd)" \
  --python-bin "$(pwd)/.venv/bin/python" \
  --evidence-root "$HOME/repos" \
  --evidence-root "$HOME/Documents" \
  --repo-context-json "$PROJECTS_ROOT/generated/github-repository-context.json" \
  --surface-context-json "$PROJECTS_ROOT/estate/surfaces.json" \
  --enable
```

Without `--enable`, the command installs/replaces the units and runtime
environment, reloads the user manager, and leaves timers disabled. This is the
preferred first install when credentials, governance context, or artifact roots
still need review.

With `--enable`, the installer enables and starts:

- `office-compile.timer`
- `staff-briefs.timer`
- `evidence-daily.timer`

Expected schedules remain: Office at 08:05/12:05/16:05/20:05, staff at
08:10/16:10, and evidence at 23:00, with persistent catch-up where declared by
the tracked timers.

## Runtime path

The services enter through one bounded routine adapter:

```text
systemd service
  -> runtime.env
  -> src/office_runtime/scripts/systemd_entrypoint.sh
  -> src/office_runtime/scripts/office_run.sh
  -> python -m office_runtime.cli ...
```

`office_run.sh` derives the repository root from its own location and uses the
configured `OFFICE_PYTHON`. The scheduled adapter accepts only the three declared
routines; an unknown routine fails instead of passing arbitrary shell commands.

Evidence roots are stored as a colon-separated list in `runtime.env`. The
installer rejects evidence paths containing `:` so parsing is unambiguous.
Governance context paths are stored separately and are never folded into the
evidence-root list.

## Verification

```bash
systemctl --user list-timers --all
systemctl --user status office-compile.timer staff-briefs.timer evidence-daily.timer
journalctl --user -u office-compile.service -n 50 --no-pager
cat ~/.config/office-auto-lab/runtime.env
```

When surface context is configured, a successful Office compile should include a
`surface_context` block in `manifest.json` and an `Estate Surface Context`
section in `office_summary.md`. Those are visibility/health outputs, not routing
commands.

Reconcile service exit status with domain artifacts: Office manifest/latest,
staff indexes, or evidence JSONL. The wrapper preserves child exit codes and
writes local logs, but neither a green timer nor a green syntax check proves
artifact correctness.

## Upgrade

After moving the checkout, changing virtual environments, changing evidence
roots, switching the authoritative `projects` checkout, or changing governance
context paths, re-run the same `install` command with the new absolute values.
The installer replaces the tracked units/configuration and reloads the user
manager. There is no second hand-maintained unit copy.

## Uninstall

```bash
PYTHONPATH=src python3 src/office_runtime/scripts/install_systemd.py uninstall
```

This disables the tracked timers, removes the installed units, and reloads the
user manager. Add `--purge-config` to also remove
`~/.config/office-auto-lab/runtime.env`.

## Recovery

On failure, stop the affected timer, inspect the journal plus runtime
logs/artifacts, correct the dependency/profile or installed runtime configuration,
re-run `install` without `--enable`, and manually start the affected service once
before re-enabling timers.

If a configured context file was moved, deleted, or replaced with the wrong
contract, fix the control-plane artifact/path and re-run the installer rather than
silently removing governance context from the live runtime.

Stop if paths, credentials, Python environment, governance authority, or artifact
ownership are ambiguous. See [failure recovery](failure-recovery.md).
